Сканирование и генерация SBOM-артефактов **включаются** настройкой `build.sbom.enable` и, при необходимости, **конфигурируются** глобально (секция `build.sbom`) или для конкретного образа (например, `image.sbom.gost`).

Разделение работы со SBOM между ролями (разработчик модуля и ответственный за SBOM продукта) и пошаговые процессы описаны на странице [«Роли и процесс работы со SBOM»]({{ "/usage/build/sbom_workflow.html" | true_relative_url }}).

Результат сканирования сохраняется исключительно в container registry как OCI-артефакт, прикреплённый к соответствующему образу. **Флаг `--repo` обязателен**: если SBOM включён, но `--repo` не указан, сборка завершается ошибкой:

```
SBOM generation requires a container registry (specify --repo)
```

## Технические ограничения

- Поддерживается только **Docker backend**.
- Поддерживается только **Stapel-синтаксис** описания образов (`werf.yaml`).
- **В shell-стадиях отключена сеть**: скачать зависимости командой в любой shell-стадии (`beforeInstall`, `install`, `beforeSetup`, `setup`) не получится — установка зависимостей выполняется только декларативно через [директиву `packages`]({{ "/usage/build/stapel/instructions.html#установка-бинарных-пакетов" | true_relative_url }}). Это и гарантирует, что все зависимости учтены в SBOM.
- SBOM формируется из **контролируемых входов**: каждая запись `packages` учитывается своим каталогизатором (для file-based типов syft читает манифест/lock-файл — `go.sum`, `package-lock.json` и т.п.; для `os-pm` — отдельный каталогизатор). Список поддерживаемых экосистем фиксированный.
- **Vendored-зависимости не учитываются**: зависимости, положенные в репозиторий напрямую (`vendor/`, `third_party/` и т.п.), проходят мимо `packages` и не попадают в SBOM. Не используйте vendoring — все зависимости должны заезжать через `packages`.
- SBOM существует только у образов, собранных с `build.sbom.enable: true` — у ранее собранных образов SBOM нет, их нужно пересобрать.

## Глобальная конфигурация проекта (`build.sbom`)

Следующие параметры активируют процесс сканирования для всех образов проекта:
1. Установите `build.sbom.enable: true`, чтобы включить функцию.
2. Задайте стандарт вывода через `standard: cyclonedx@1.6` (на данный момент поддерживается только `cyclonedx@1.6`).

```yaml
project: werf-sbom-meta-example
configVersion: 1
build:
  sbom:
    enable: true
    standard: cyclonedx@1.6
```

Сейчас данная опция использует следующие _умолчания_:

| Свойство                                  | Значение                                                                                 |
|-------------------------------------------|------------------------------------------------------------------------------------------|
| **Сканер**                                | syft                                                                                     |
| **Образ сканера**                         | anchore/syft:v1.45.1                                                             |
| **Политика получения образа**             | `PullIfMissing`                                                                          |
| **Способ подключения к источнику данных** | daemon + socket via volume (для Docker) |
| **Путь в образе источнике**               | корень OS                                                                                |
| **Настройки сканирования**                | [ссылка](https://github.com/anchore/syft/wiki/Configuration#list-of-configurable-values) |
| **Исходящий стандарт**                    | `CycloneDX@1.6`                                                                          |
| **Исходящий формат**                      | `JSON`                                                                                   |

## Требования к базовому образу

Когда генерация SBOM включена, каждый базовый образ, указанный через `from` или `fromImage`, и каждый образ, указанный через `import`, **должен иметь прикреплённый SBOM-артефакт в registry**. Альтернативы этому требованию нет; единственное исключение описано ниже.

Если образ не имеет прикреплённого SBOM, сборка завершается ошибкой с сообщением о том, что базовый образ должен иметь прикреплённый SBOM-артефакт.

Чтобы устранить ошибку, пересоберите базовый образ с `build.sbom.enable: true`.

Если базовый образ — `scratch`, он создаёт пустой SBOM без компонентов.

### Устаревшее исключение (deprecated)

Два семейства старых сборочных образов Deckhouse не имеют прикреплённого SBOM:

- `registry.deckhouse.io/container-factory/builder/golang` (и его теги)
- `registry.deckhouse.io/container-factory/builder/alpine` (и его теги)

Сборки с такими образами пока завершаются успешно, но выдают предупреждение:

```
The builder image "..." is DEPRECATED and it WILL CAUSE AN ERROR in the future.
Plan your migration to an up-to-date builder image.
```

Любой другой сборочный образ Deckhouse, не имеющий SBOM, включая более новые образы `container-factory`, завершит сборку ошибкой:

```
the base image "..." must have an SBOM artifact attached;
the image is a builder image but SBOM is required
```

Такие образы нужно пересобрать с `build.sbom.enable: true`, чтобы прикрепить SBOM.

## Как хранится SBOM

SBOM хранится как OCI-артефакт, subject которого указывает на манифест целевого образа. Это делает его обнаруживаемым любым инструментом, который понимает OCI referrers.

### Структура артефакта

Документ CycloneDX упаковывается в [in-toto](https://in-toto.io/) statement, а затем в [DSSE](https://github.com/secure-systems-lab/dsse) envelope перед сохранением. Слой с envelope имеет media type `application/vnd.dsse.envelope.v1+json`; predicate type в in-toto statement равен `https://cyclonedx.org/bom/v1.6`.

### Совместимость с registry

werf всегда использует индекс на основе тегов для сохранения и получения SBOM-артефактов, независимо от того, поддерживает ли registry OCI referrers API. Никакая конфигурация, специфичная для registry, не требуется. Кроме того, werf устанавливает поле OCI `subject` в манифесте артефакта, что позволяет внешним инструментам, понимающим спецификацию OCI referrers, обнаруживать и получать SBOM напрямую. Оба пути доступа поддерживаются автоматически при каждой публикации.

### Аннотации артефакта

Каждый SBOM-артефакт несёт следующие аннотации в своём дескрипторе в индексе:

| Аннотация | Содержимое |
|---|---|
| `io.werf.image-name` | Имя образа, к которому относится данный SBOM |
| `io.werf.checksum` | Контрольная сумма содержимого образа |
| `io.werf.target-platform` | Целевая платформа CPU/OS (например, `linux/amd64`) |

### Мультиплатформенные образы

При сборке мультиплатформенного образа werf генерирует отдельный SBOM-артефакт для каждой платформы. Каждый SBOM аннотируется значением `io.werf.target-platform`, чтобы инструменты могли получить нужный.

## Свойства безопасности ГОСТ (`sbom.gost`)

Для соответствия стандартам безопасности ГОСТ можно настроить обязательные свойства безопасности для всех компонентов в SBOM. Эти свойства будут внедрены во все прямые компоненты итогового SBOM. По умолчанию как генерируемый, так и определяемый пользователем SBOM-ы обогащаются значениями `attackSurface=yes` и `securityFunction=yes`, если не задано иное через настройки проекта (meta-уровень) или конкретного образа (image-уровень).

1. `attackSurface`: Свойство поверхности атаки (`yes` | `no` | `indirect`).
2. `securityFunction`: Свойство функции безопасности (`yes` | `no` | `indirect`).

Эти свойства можно определить глобально в `build.sbom.gost` или для конкретного образа в `image.sbom.gost`. Конфигурация на уровне образа переопределяет глобальную конфигурацию.

> **ПРИМЕЧАНИЕ:** Интеграция свойств ГОСТ является экспериментальной и строго привязана к стандарту `cyclonedx@1.6`.

Пример:
```yaml
build:
  sbom:
    enable: true
    standard: cyclonedx@1.6
    gost:
      attackSurface: yes
      securityFunction: no
```

## Обогащение VCS external references

При включённом SBOM werf на этапе сборки обогащает компоненты VCS external references через внешний сервис разрешения purl. URL сервиса задаётся переменной окружения `WERF_EXTERNAL_REFS_SERVER_URL` (CLI-флага нет):

```bash
export WERF_EXTERNAL_REFS_SERVER_URL="https://purl-resolver.example.com/"
```

Если `build.sbom.enable: true`, переменная **обязательна** — без неё сборка завершается ошибкой:

```
WERF_EXTERNAL_REFS_SERVER_URL env var is required
```

При выключенном SBOM переменная не используется.

## Подписание SBOM

Подписание SBOM — опциональный шаг сборки. Оно включается, если команде `werf build` передан ключ подписи:

| Флаг | Переменная окружения | Назначение |
|---|---|---|
| `--sign-key` | `WERF_SIGN_KEY` | приватный ключ: путь к PEM-файлу, base64-кодированный PEM или `hashivault://[KEY]` |
| `--sign-cert` | `WERF_SIGN_CERT` | leaf-сертификат: путь к PEM-файлу или base64-кодированный PEM |
| `--sign-intermediates` | `WERF_SIGN_INTERMEDIATES` | промежуточные сертификаты: путь к PEM-файлу или base64-кодированный PEM |

Если `--sign-key` не задан, SBOM генерируется и публикуется неподписанным — это не ошибка.

Команды `werf sbom get`, `werf sbom merge` и `werf sbom validate` флагов подписи не принимают: `get` выгружает артефакт как есть, `merge` и `validate` работают с уже выгруженными SBOM. Проверить подпись SBOM-артефакта можно командой `werf attest verify` с публичным ключом (`--key`).

## Кеширование и пересборка

Переключение `build.sbom.enable` изменяет дайджест стадии, поэтому включение или выключение генерации SBOM инвалидирует кеш и запускает полную пересборку.

Пока генерация SBOM выключена (это значение по умолчанию), дайджесты стадий идентичны дайджестам проекта, который никогда не использовал эту возможность. Кеши, собранные до появления поддержки SBOM, остаются валидными и продолжают переиспользоваться. Если включить фичу, а затем снова выключить, дайджесты возвращаются к исходным значениям.

Изменение свойств ГОСТ (`sbom.gost`) на дайджест стадии не влияет. Закешированные стадии переиспользуются, а документ SBOM перегенерируется с новыми свойствами во время шага SBOM.

## Просмотр и объединение SBOM

[`werf sbom get`]({{ "/reference/cli/werf_sbom_get.html" | true_relative_url }}) получает SBOM образа, описанного в `werf.yaml`, и выводит его в stdout. SBOM читается как OCI-артефакт из container registry, поэтому флаг `--repo` обязателен. При обращении по имени образа команда запускает стандартный сборочный конвейер werf: отсутствующие стадии и SBOM-артефакты досоздаются, как при `werf build` (с флагом `--require-built-images` команда вместо этого завершается ошибкой). Для выбора конкретной версии поддерживаются флаги `--tag` и `--digest` (взаимоисключающие) — в этом режиме команда только выгружает готовый SBOM и завершается ошибкой, если он не найден.

[`werf sbom merge`]({{ "/reference/cli/werf_sbom_merge.html" | true_relative_url }}) собирает SBOM уровня продукта из нескольких пообразных SBOM. На вход принимается JSON-файл с соответствием «имя образа → sha256-дайджест»; команда скачивает отдельные SBOM из registry и объединяет их в один CycloneDX-документ с сохранением графов зависимостей. Поддерживаются два выходных формата ИСПРАС: `container` (иерархический, каждый образ становится компонентом верхнего уровня с вложенными пакетами) и `oss` (плоский, все пакеты дедуплицируются в один список). Свойства ГОСТ `attack_surface` и `security_function` агрегируются снизу вверх по приоритету `yes > indirect > no`.

[`werf sbom validate`]({{ "/reference/cli/werf_sbom_validate.html" | true_relative_url }}) проверяет CycloneDX JSON-файл по схемам ИСПРАС. Команда запускает sbom-checker в Docker-контейнере и выводит обнаруженные нарушения. Поддерживаются типы SBOM `oss` и `container`.
