Из-за используемых инструментов сборки либо просто из-за исходных файлов размер целевого образа может увеличиваться в несколько раз. Зачастую эти файлы не нужны в конечном образе. Для решения таких проблем сообщество Docker предлагает выполнять установки инструментов, сборку и удаление ненужных файлов за один шаг.

Условный пример:
```Dockerfile
RUN “download-source && cmd && cmd2 && remove-source”
```

> Аналогичный пример может быть реализован и в werf. Для этого достаточно описать инструкции в одной _пользовательской стадии_. Пример при использовании _shell-сборщика_ для стадии _install_:
```yaml
shell:
  install:
  - "download-source"
  - "cmd"
  - "cmd2"
  - "remove-source"
```

Однако при использовании такого метода кэширование работать не будет, и установка инструментов сборки будет выполняться каждый раз.

Другой способ — использование multi-stage сборки, которая поддерживается в Docker, начиная с версии 17.05.

```Dockerfile
FROM node:latest AS storefront
WORKDIR /app
COPY react-app .
RUN npm install
RUN npm run build

FROM maven:latest AS appserver
WORKDIR /app
COPY . .
RUN mvn package

FROM java:8-jdk-alpine
COPY --from=storefront /app/react-app/build/ /static
COPY --from=appserver /app/target/AtSea-0.0.1-SNAPSHOT.jar /app/AtSea.jar
```

Смысл такого подхода в следующем — описать несколько вспомогательных образов и выборочно копировать артефакты из одного образа в другой, оставляя все то, что не нужно в конечном образе.

werf предлагает подобный подход.

> Почему werf не использует multi-stage сборку?
* Исторически возможность _импорта_ появилась значительно раньше, чем в Docker появилась multi-stage сборка.
* werf дает больше гибкости при работе со вспомогательными образами.

## Конфигурация импорта

Импорт _ресурсов_ из _образов_ должен быть описан в директиве `import` в конфигурации _образа_, куда импортируются файлы. `import` — массив записей, каждая из которых должна содержать следующие параметры:

- `from: <image name>`: _исходный образ_, имя образа из которого вы хотите копировать файлы или каталоги. Поддерживается как импорт из образов текущего проекта, так и внешние образы в формате `image_name:tag` или `image_name@digest`
- `add: <absolute path>`: _исходный путь_, абсолютный путь к файлу или каталогу в _исходном образе_ для копирования.
- `to: <absolute path>`: _путь назначения_, абсолютный путь в _образе назначения_ (куда импортируются файлы или каталоги). В случае отсутствия считается равным значению, указанному в параметре `add`.
- `before: <install || setup>` or `after: <install || setup>`: _стадия образа назначения_ для импорта. В настоящий момент возможен импорт только до/после стадии _install_ или _setup_.

Пример:
```yaml
import:
  - from: application-assets
    add: /app/public/assets
    to: /var/www/site/assets
    after: install
  - from: node:20-alpine
    add: /usr/share/nginx/html
    to: /var/www/site/prebuilt
    after: setup
```

Так же, как и при конфигурации _git mappings_, поддерживаются маски включения и исключения файлов и каталогов.
Для указания маски включения файлов используется параметр `includePaths: []`, а для исключения `excludePaths: []`. Маски указываются относительно пути источника (параметр `add`).
Вы также можете указывать владельца и группу для импортируемых ресурсов с помощью параметров `owner: <owner>` и `group: <group>` соответственно.
Это поведение аналогично используемому при добавлении кода из Git-репозиториев, и вы можете подробнее почитать об этом [в соответствующем разделе]({{ "usage/build/stapel/git.html" | true_relative_url }}).

> Обратите внимание, что путь импортируемых ресурсов и путь указанный в _git mappings_ не должны пересекаться.

### Правила пути назначения

Что окажется по _пути назначения_, зависит от того, каталог или файл указан в _исходном пути_.

Если `add` — это **каталог**, его содержимое сливается в `to`. Уже лежащие в `to` файлы сохраняются, а файлы с совпадающими именами перезаписываются. Именно поэтому несколько импортов могут вести в один и тот же каталог.

Если `add` — это **файл**, результат зависит от _образа назначения_:

- если пути `to` не существует, файл создаётся ровно по этому пути: `add: /app/config.yaml` с `to: /etc/app.yaml` даёт `/etc/app.yaml`;
- если `to` уже существует и это каталог, файл помещается внутрь него: тот же импорт с `to: /etc` даёт `/etc/config.yaml`.

werf создаёт только родительский каталог для `to`, поэтому существует ли сам `to`, определяет _образ назначения_ — когда разница важна, указывайте полный путь до файла.

Завершающий слеш в `to` (всё, кроме `to: /`) — ошибка конфигурации, сборка падает: пишите `to: /usr/sbin`, а не `to: /usr/sbin/`.

## Подписание файлов внутри образа

Директива `sign` подписывает файл, который производит образ, и кладёт подпись рядом с ним, не давая сборочной стадии доступ к ключу подписи. Она занимает в цепочке стадий то же место, что и `import`: файл должен существовать после стадии, указанной в `before` или `after`, а подпись доступна последующим стадиям.

```yaml
image: sysext
from: registry.example.com/base/ubuntu:22.04
shell:
  install:
  - mkfs.erofs /out/ext.raw /src
  - veritysetup format --root-hash-file=/out/ext.roothash /out/ext.raw /out/ext.verity
sign:
- path: /out/ext.roothash
  after: install
```

werf читает файл из собранного к этому моменту образа, подписывает его на сборочном хосте и добавляет `<path>.p7s` новым слоем. Подпись — отсоединённый PKCS#7 (CMS) `SignedData` над содержимым файла: SHA-256, RSASSA-PKCS1-v1_5, без аутентифицированных атрибутов, со встроенным сертификатом подписанта — ровно та форма, которую производит `systemd-keyutil pkcs7`, поэтому systemd и ядро Linux принимают её как подпись dm-verity root hash. Ключ, соответственно, должен быть RSA.

Ключ и сертификат никогда не являются частью `werf.yaml`; они передаются только через командную строку, отдельно от ключа подписи манифеста и SBOM:

| Флаг | Переменная окружения | Описание |
|---|---|---|
| `--sign-files` | `WERF_SIGN_FILES` | обрабатывать директивы `sign` (по умолчанию `true`); `false` пропускает их и собирает образ без подписей |
| `--sign-files-key` | `WERF_SIGN_FILES_KEY` | приватный ключ: путь к PEM-файлу, PEM в base64 или `hashivault://[KEY]` |
| `--sign-files-cert` | `WERF_SIGN_FILES_CERT` | сертификат подписанта: путь к PEM-файлу или PEM в base64 |
| `--sign-files-intermediates` | `WERF_SIGN_FILES_INTERMEDIATES` | промежуточные сертификаты: путь к PEM-файлу или PEM в base64 |

Сборка образа с директивой `sign` завершается ошибкой ещё до запуска стадий, если ключ или сертификат не заданы, а `--sign-files` не равен `false`. Команды, которые не собирают образы (`lint`, `stages copy`, `sbom get`), не имеют флага `--sign-files` и считают его выключенным: такой `werf.yaml` они принимают без ключа.

С `hashivault://` приватный ключ не покидает KMS. Сертификат из KMS не запрашивается: если его выпускает PKI (например, Vault PKI), пайплайн сам получает PEM и передаёт его путём или в base64. Контейнер стадии всегда запускается с `network: none` независимо от настройки `network` образа, и команды образа в нём не выполняются, поэтому директива работает без изменений при `build.sbom.enable: true`, когда [в shell-стадиях отключена сеть]({{ "/usage/build/sbom.html" | true_relative_url }}).

Стадия кэшируется как любая другая. Её дайджест включает подписываемые пути и сертификат подписанта, поэтому ротация ключа пересобирает подпись и последующие стадии, а повторная сборка с тем же ключом переиспользует закэшированный слой. В `.p7s` встраивается только сертификат подписанта; промежуточные сертификаты не участвуют ни в подписи, ни в дайджесте.
