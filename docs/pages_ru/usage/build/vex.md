[VEX](https://openvex.dev/) (Vulnerability Exploitability eXchange) — это документ, который для конкретного продукта сообщает, подвержен ли он определённым уязвимостям: CVE, найденная сканером в компоненте образа, может быть неэксплуатируемой, потому что уязвимый код никогда не выполняется, нейтрализован конфигурацией или уже исправлен. werf прикрепляет такой документ к собранному образу как OCI-артефакт рядом со [SBOM]({{ "/usage/build/sbom.html" | true_relative_url }}), чтобы сканеры уязвимостей и инструменты аудита могли читать оба документа из registry.

VEX-документ **прикрепляется к конкретному образу** директивой `vex` в `werf.yaml`. werf не генерирует VEX-утверждения: документ пишет сопровождающий образа, он коммитится в Git-репозиторий и публикуется вместе с образом. Публикация не зависит от генерации SBOM: образ может нести VEX-документ как с `build.sbom.enable: true`, так и без него.

## Конфигурация в `werf.yaml`

Директива `vex` доступна как для Dockerfile-, так и для Stapel-образов. Значение — путь к JSON-документу [OpenVEX](https://github.com/openvex/spec) относительно директории проекта, в короткой или полной форме:

```yaml
project: my-project
configVersion: 1
---
image: app
dockerfile: Dockerfile
vex: vex/app.openvex.json
---
image: worker
from: registry.werf.io/werf/scratch:latest
git:
  - add: /
    to: /app
    excludePaths:
      - vex
vex:
  document: vex/worker.openvex.json
```

Обе формы эквивалентны; пустое значение отклоняется:

```
`vex` directive must specify a VEX document path, use `vex: PATH` or `vex:
  document: PATH`
```

### Требования к документу

Документ читается и проверяется при разборе `werf.yaml`, поэтому некорректный документ ломает любую команду, читающую конфигурацию, а не только `werf build`. Документ должен:

- существовать и быть обычным файлом по указанному пути;
- быть валидным JSON;
- быть JSON-объектом с `"@context": "https://openvex.dev/ns/v0.2.0"` — контекстом OpenVEX, сравниваемым точно.

Иначе разбор конфигурации завершается одной из ошибок:

```
unable to read VEX file "vex/app.openvex.json": ...
invalid VEX document "vex/app.openvex.json": VEX document is not valid JSON
invalid VEX document "vex/app.openvex.json": VEX document has unexpected @context "...", expected "https://openvex.dev/ns/v0.2.0"
```

Минимальный документ:

```json
{
  "@context": "https://openvex.dev/ns/v0.2.0",
  "@id": "https://example.com/vex/app-2024-06-01",
  "author": "Security team <security@example.com>",
  "timestamp": "2024-06-01T00:00:00Z",
  "version": 1,
  "statements": [
    {
      "vulnerability": {"name": "CVE-2024-12345"},
      "products": [{"@id": "pkg:oci/app"}],
      "status": "not_affected",
      "justification": "vulnerable_code_not_in_execute_path",
      "impact_statement": "The vulnerable function is never called in this build."
    }
  ]
}
```

werf проверяет только то, что документ — это JSON с контекстом OpenVEX в `@context`; остальное содержимое — наличие и состав `statements`, `status`, `justification`, `products` — не проверяется и остаётся на ответственности автора и инструментов, которые потребляют документ.

### Гитерминизм

Как и сам `werf.yaml`, VEX-документ читается из текущего коммита: незакоммиченный или неотслеживаемый документ роняет сборку обычной для гитерминизма ошибкой. Для разработки работает флаг `--dev`, как и для любого другого файла. Чтобы постоянно разрешить чтение определённых VEX-документов из рабочей директории, перечислите их в `werf-giterminism.yaml`:

```yaml
giterminismConfigVersion: 1
config:
  vex:
    allowUncommitted:
      - vex/*.openvex.json
```

О последствиях см. раздел [о гитерминизме]({{ "/usage/project_configuration/giterminism.html#vex" | true_relative_url }}).

## Публикация

VEX-артефакт публикуется командой `werf build` (и любой командой, запускающей сборочный конвейер, например `werf converge`) после того, как образ и его стадии отправлены в registry, сразу после шага SBOM. Он хранится **только в container registry**: если сборка использует локальное хранилище (без `--repo`), шаг VEX пропускается и ничего не публикуется.

Для каждого образа с директивой `vex` в логе появляется одна из строк:

```
image app: Published VEX artifact
image app: VEX artifact is up to date — skipping publish
```

Артефакт публикуется в репозиторий стадий (`--repo`) и копируется оттуда в финальный репозиторий (`--final-repo`) вместе с образом. Для одноплатформенного образа он копируется и в кеширующие репозитории (`--cache-repo`); VEX-артефакт мультиплатформенного образа прикреплён к индексу образа, которого в кеширующем репозитории не бывает, поэтому туда он не копируется. Вторичные репозитории (`--secondary-repo`) доступны только для чтения и ничего не получают. Копирование выполняется при каждой сборке, поэтому репозиторий, в котором образ лежит без своих артефактов, будет дополнен следующим запуском.

С флагом `--check-built-images` ничего не публикуется, включая VEX-артефакты: команда только проверяет, что образы уже существуют. `--require-built-images` (`-Z`) — не режим проверки: он публикует ранее собранные образы без выполнения сборочных инструкций, и шаг VEX выполняется как при обычной сборке.

### Мультиплатформенные образы

В отличие от SBOM, который создаётся для каждой платформы, VEX-документ описывает образ целиком. Для мультиплатформенного образа werf публикует **один** VEX-артефакт, прикреплённый к дайджесту индекса образа, а не к манифестам платформ. Поэтому `werf attest get` и `werf attest verify` с `--type openvex` отклоняют `--platform`, если ссылка указывает на индекс.

## Как хранится VEX-артефакт

VEX-артефакт хранится как OCI-артефакт, subject которого указывает на манифест (или индекс) целевого образа, так же как и [SBOM]({{ "/usage/build/sbom.html#как-хранится-sbom" | true_relative_url }}): werf поддерживает индекс на основе тегов, работающий с любым registry, и дополнительно устанавливает поле OCI `subject` для инструментов, понимающих OCI referrers API.

### Структура артефакта

Документ OpenVEX упаковывается в [in-toto](https://in-toto.io/) statement, а затем в [DSSE](https://github.com/secure-systems-lab/dsse) envelope. Форма артефакта зависит от того, была ли сборка подписана:

| | Неподписанная сборка | Подписанная сборка (`--sign-key`) |
|---|---|---|
| Media type слоя | `application/vnd.dsse.envelope.v1+json` | `application/vnd.dev.sigstore.bundle.v0.3+json` (Sigstore bundle с подписанным DSSE envelope и подсказкой о публичном ключе) |
| Predicate type in-toto | `https://openvex.dev/ns/v0.2.0` | `https://openvex.dev/ns` |

Подписанная форма использует URI predicate без версии, потому что именно в него cosign разрешает well-known тип `openvex`, — так подписанный VEX-артефакт проверяется и стандартным cosign, и `werf attest verify`. Оба URI обозначают один и тот же вид артефакта: `werf attest get --type openvex` находит любой из них.

werf хранит ровно один опубликованный сборкой VEX-артефакт на образ: публикация подписанного артефакта заменяет неподписанный и наоборот, поэтому читатель никогда не получит устаревший артефакт предыдущего состояния подписи. Аттестация, прикреплённая вручную командой `werf attest sign`, хранится отдельно от опубликованной сборкой (свои артефакты werf узнаёт по аннотации `io.werf.checksum`), и `werf attest get` / `werf attest verify` предпочитают прикреплённую вручную, если есть обе.

### Аннотации артефакта

Каждый VEX-артефакт несёт следующие аннотации в своём дескрипторе в индексе:

| Аннотация | Содержимое |
|---|---|
| `io.werf.image-name` | Имя образа, к которому относится VEX-документ |
| `io.werf.checksum` | Кеш-идентичность артефакта (см. [Кеширование и пересборка](#кеширование-и-пересборка)) |
| `io.werf.target-platform` | Целевая платформа одноплатформенного образа (например, `linux/amd64`) |
| `dev.sigstore.bundle.predicateType` | Predicate type in-toto, чтобы вид артефакта распознавался без скачивания слоя |

## Подпись VEX

Подпись VEX использует те же флаги, что и [подписание SBOM]({{ "/usage/build/sbom.html#подписание-sbom" | true_relative_url }}), и включается передачей ключа подписи в `werf build`:

| Флаг | Переменная окружения | Назначение |
|---|---|---|
| `--sign-key` | `WERF_SIGN_KEY` | приватный ключ: путь к PEM-файлу, PEM в base64 или `hashivault://[KEY]` |
| `--sign-cert` | `WERF_SIGN_CERT` | листовой сертификат: путь к PEM-файлу или PEM в base64 |
| `--sign-intermediates` | `WERF_SIGN_INTERMEDIATES` | промежуточные сертификаты: путь к PEM-файлу или PEM в base64 |

Если `--sign-key` не задан, VEX-документ публикуется неподписанным — это не ошибка. Один и тот же ключ подписывает SBOM и VEX-артефакт в рамках одной сборки.

Проверить подпись можно командой `werf attest verify --type openvex` с публичным ключом (`--key`), см. ниже.

## Кеширование и пересборка

Директива `vex` и содержимое документа **не участвуют в дайджестах стадий**: добавление, изменение или удаление VEX-документа само по себе не пересобирает образ. Меняется только артефакт. Это верно, пока документ не входит в сборочный контекст: VEX-файл внутри `git`-маппинга Stapel-образа или копируемый Dockerfile-инструкцией `COPY`/`ADD` — обычное содержимое образа, и его правка пересобирает образ как любой другой файл; держите документ вне путей, попадающих в образ (см. `excludePaths` в примере выше).

Нужно ли переопубликовать артефакт, решает его контрольная сумма (`io.werf.checksum`), вычисляемая из содержимого документа, дайджеста образа, к которому он прикреплён, отпечатка ключа подписи (пустого для неподписанной сборки) и версии формата артефакта. Сборка переопубликовывает артефакт, если хоть что-то из этого отличается от уже лежащего в registry, и пропускает публикацию в противном случае. На практике это означает:

- правка документа и пересборка публикует новые утверждения под тем же дайджестом образа — обычный способ отреагировать на новую CVE без пересборки образа;
- включение подписи, ротация ключа или отказ от подписи переопубликовывают артефакт;
- пересборка без изменений сообщает `VEX artifact is up to date — skipping publish`.

VEX-артефакт есть только у образов, собранных после добавления директивы `vex`, — у ранее собранных образов его нет до следующей сборки с `--repo`.

## Работа с VEX-аттестациями

VEX-документами управляют общие команды для аттестаций из группы [`werf attest`]({{ "/reference/cli/werf_attest_get.html" | true_relative_url }}). Все они читают registry, поэтому `--repo` обязателен, а образ задаётся через `--tag` или `--digest` (взаимоисключающие); `--image` сужает поиск до одного имени образа, если несколько образов делят один дайджест.

[`werf attest ls`]({{ "/reference/cli/werf_attest_ls.html" | true_relative_url }}) перечисляет аттестации, прикреплённые к образу, с их predicate type, дайджестом и признаком подписи. Для одноплатформенного образа в список входит и VEX-документ; для мультиплатформенного команда обходит только манифесты платформ, поэтому VEX-артефакт, прикреплённый к индексу, в список не попадает — проверяйте его через `werf attest get --type openvex`:

```shell
werf attest ls --repo registry.example.com/project --tag app-1.2.3
```

[`werf attest get`]({{ "/reference/cli/werf_attest_get.html" | true_relative_url }}) скачивает аттестацию, снимает DSSE envelope и in-toto statement и печатает документ OpenVEX в stdout **без** проверки подписи:

```shell
werf attest get --type openvex --repo registry.example.com/project --tag app-1.2.3 > app.openvex.json
```

[`werf attest verify`]({{ "/reference/cli/werf_attest_verify.html" | true_relative_url }}) делает то же самое после проверки подписи DSSE одним или несколькими публичными ключами (`--key`, повторяемый, достаточно одного совпадения); неподписанный или неверно подписанный артефакт завершает команду ошибкой без вывода:

```shell
werf attest verify --type openvex --key vex-signer.pub --repo registry.example.com/project --digest sha256:...
```

[`werf attest sign`]({{ "/reference/cli/werf_attest_sign.html" | true_relative_url }}) подписывает произвольный файл predicate (`--predicate`) ключом `--sign-key` и прикрепляет его к образу. Он не заменяет опубликованный сборкой VEX-артефакт и не заменяется следующей сборкой; пока существуют оба, `werf attest get` и `werf attest verify` возвращают прикреплённый вручную. Чтобы обновить VEX-утверждения образа, правьте документ в Git и пересобирайте.

`--type` принимает well-known имена `openvex`, `cyclonedx`, `slsaprovenance`, `slsaprovenance1`, `spdxjson` или полный URI predicate.
